# ZCode Start Plan

`src/adapters/zai-plan.ts` preserves caller system instructions after two product identity blocks: the product prefix and combined stable identity/desktop block. The stable sections use one newline separator, and no invented unknown-host Environment block is added. The prefix has no cache breakpoint. Account metadata comes from the selected bearer rather than an unrelated active account. Coding-key requests never silently change to Start Plan after a quota refusal.

`src/oauth/zai-plan-policy.ts` reads public client policy without account headers, using bounded reads and a short cache. `src/adapters/zai-plan-transport.ts` uses direct HTTP streaming when model CAPTCHA is skipped or policy is unknown. Explicit CAPTCHA refusals enable at most three total inference dispatches through the existing browser transport; the shared send budget may stop recovery sooner. Successful streams and other refusals are never replayed by this transport.

Inference dispatch uses the shared physical-send budget and pacing seam. The caller's abort signal remains attached after response headers; the header deadline is cleared when headers arrive. Public policy requests do not count as inference sends. Browser loading and verification occur only after a CAPTCHA recovery dispatch has been admitted.

`src/oauth/zai-plan.ts` defaults to client version 3.16.3. An exact `x.y.z` `OPENCODEX_ZCODE_APP_VERSION` override is read at process startup. Platform headers describe the executing host. JWT model requests carry both bearer and API-key headers to the canonical ZCode endpoint.

Explicit JWT expiry is respected during local login, request building and refresh. A missing expiry remains compatible with older tokens. Refresh can reimport a matching Desktop identity, but cannot replace an existing account with a different Desktop user or extend an unchanged token's lifetime. There is no remote JWT refresh call.
The modern Desktop credential file is authoritative: an unusable file does not restore a different legacy login. Expired imports are rejected before persistence. Manual login completion cancels the losing browser poll.

`tests/oauth/zai-plan-transport.test.ts` verifies system and tool preservation, direct streams in parallel, explicit challenge recovery, refusal continuity, send-budget admission and cancellation. `tests/oauth/zai-plan-fingerprint.test.ts` retains browser lifecycle and metadata coverage; `tests/oauth/zai-plan-quota.test.ts` distinguishes quota refusals from model output. These offline tests do not assert live account entitlement or inference success.

## Account entitlement and model discovery

The ZCode registry declares `GLM-5.3-Flash` as native text/image input and `GLM-5.3` as text-only with the existing vision sidecar. Registry enrichment fills these hints into saved providers that omitted them, so client exports do not default Flash to text-only. The Anthropic adapter retains image blocks on the Flash wire path; offline coverage lives in `tests/oauth/zai-plan-transport.test.ts`.

`src/oauth/zai-plan-balance.ts` reads the canonical billing balance endpoint with the selected bearer and its device header. The summary contains no billing/account identifiers. Active plans and unexpired token buckets determine entitlement; `model_usage`/`token` buckets with explicit `model:*` capabilities supply exact model IDs. Marketing labels cannot grant access. Pending activation and expiry cap the cache lifetime, with a maximum of 60 seconds; failed reads become unknown rather than stale positive evidence. The bounded cache is credential/device/version-scoped and starts no polling timer.

`src/providers/quota/zai-plan.ts` projects exact-model windows through the existing account quota API. `src/cli/account.ts` displays the first two exact model windows in its compact table; JSON retains the full breakdown. `src/providers/quota/account-cache.ts` includes device identity in the credential fence. `src/oauth/account-quota-rank.ts` ranks only matching fresh model windows; exhausting Flash does not exhaust GLM-5.3. `src/adapters/zai-plan-models.ts` and `src/codex/catalog/provider-models.ts` discover callable models from that bearer account's positive entitlement. Explicit static catalogs remain static; discovery failures retain a degraded configured roster.

## Refusal and account continuity

`src/oauth/zai-plan-health.ts` checks the bound account before policy lookup and again after pacing/verification. Removed, paused, changed or reauthentication-required accounts cannot dispatch. The original credential/device generation also fences late refusals. Risk code 3012 or a canonical POST's 405 refusal cools only the served account for 15 minutes through the shared pool; 429 honors bounded Retry-After; authentication refusals mark only the matching generation for re-login. A 402 holds only that model for 60 seconds. Three server refusals within a minute trigger an account cooldown, and a successful response clears server strikes. Successful stream bodies are not inspected, consumed or replayed.

`src/server/management/zai-plan-routes.ts` keeps cheap account lists network-free. An explicit `?balance=1` reads the active Start Plan summary; `&refresh=1` bypasses its cache. Account-qualified actions resolve their exact account and device, and unknown account IDs never fall back to the active slot. Preview tries ordinary HTTP before a bounded explicit CAPTCHA recovery. Claim, telemetry and device rotation require a dashboard session; import remains available before a first login and awaits persistence. Rotating an inactive account never changes the saved active account.

The standalone `gui/public/zai-plan.html` panel uses origin-bound GUI session metadata and CSRF for manual account actions. Copy comes from all dashboard locale catalogs through the generated locale asset. Package preview never claims automatically. Its explicit diagnostic sends one ordinary, bounded Responses request, preserving normal admission, routing and spend accounting; no management route sends inference. `src/server/management/zai-plan-diagnostic.ts` projects recent request-log provenance, rejects ambiguous account labels and identifies the actual served account before reading its balance. An opaque, bounded observation cache binds the pre-request balance to the account, login, credential and device without serializing private digests. Changed identities, model windows and unverified routes leave balance attribution unknown. The diagnostic response includes no upstream credential or request body.

`tests/oauth/zai-plan-balance.test.ts`, `tests/oauth/zai-plan-health.test.ts` and `tests/server/zai-plan-management.test.ts` cover these contracts with fake accounts and upstreams. `tests/server/zai-plan-proxy-pool.test.ts` exercises actual Responses ingress and reactive account rotation while checking the serving device and retained instructions. The current HTTP gateway retains host-owned tools; an app-server bridge would transfer tool execution to ZCode and remains a separate optional design, not a substitute for this transport.
